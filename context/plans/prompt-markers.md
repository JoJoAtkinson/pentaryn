# Prompt markers — design

**Read this when:** building or changing the prompt-marker system (`pentaryn-prompts` module, the
`prompt-markers` bridge tool, the playbook). **History, not instructions** once shipped — the
use-doc is [`../foundry/prompt-markers.md`](../foundry/prompt-markers.md).
**Not this file:** pointing at a spot with a colour/number marker → [`../foundry/markers.md`](../foundry/markers.md)

> Status: **BUILT, INSTALLED and EVALUATED 2026-10-10** (build record in section 12; sections 0-11 are the design as written). Grounded in two research passes (Foundry 14.369 /
> dnd5e 6.0.6 source, tested live with `eval-js`; context-format study with token counts).
> Facts from those passes are stated here as settled; decisions are marked **Decision**.

---

## 0. What this is, in one paragraph

Joe drops a **prompt marker** on a map, a small dialog opens with the cursor already in the
text box, he types what should be there, presses Esc, and moves on. Later he says *"process and
replace all the prompt markers"*. One tool call hands Claude every prompt on every scene, each
one already placed in its surroundings: distance and compass bearing to what is near, whether
it can be seen through the walls, which markers form a pack and which stand alone, what has
already been built nearby and from which prompt. Claude designs, then replaces each marker with
the real thing through one deterministic helper that puts it on the marker's exact footprint,
stamps the original prompt on it as provenance, and deletes the marker. Nothing geometric is
ever re-derived by the model, and nothing Joe wrote is ever retyped.

Goals, in order: **(1) speed of building world context, (2) quality of the built result,
(3) no tokens spent on programmatic steps.**

## 1. Where it lives

### 1.1 A new module: `foundry/module/pentaryn-prompts`

**Decision:** a new module, not an extension of `pentaryn-ties` or `-dropbin`. It has its own
actors, dialog, geometry and queries, and nothing else in the repo needs any of them. It
follows the house pattern: in-repo source, `make foundry-prompts-check` / `-sync` through
`scripts/foundry/ops/config.py` (`MODULES["prompts"]`, checks `(*_STATIC, "node-test")`), copied
not symlinked, API under `game.pentaryn.prompts`.

```
foundry/module/pentaryn-prompts/
  module.json            id pentaryn-prompts · esmodules [prompts.mjs] · styles [styles/prompts.css]
                         lang/en.json · relationships: dnd5e ≥ 6.0 · libWrapper optional · socket false
  prompts.mjs            entry: settings, hooks, keybindings, game.pentaryn.prompts, CONFIG.queries
  markers.mjs            the six marker actors: ensure/repair on ready, art paths, size table
  dialog.mjs             PromptDialog (ApplicationV2 + HandlebarsApplicationMixin)
  templates/prompt-dialog.hbs
  geometry-core.mjs      PURE (node-testable): bands, bearing, nearest-square distance,
                         clustering, deterministic ids, text rendering. No Foundry globals.
  los.mjs                sight tests over scene documents (polygon backend + door pass)
  model.mjs              builds the scene model (items, pairs, encounters) from documents
  gather.mjs             model → Draft-A text + manifest; stores the manifest; crops
  replace.mjs            placement, provenance, batch, dry-run
  crops.mjs              OffscreenCanvas crop renderer
  assets/
    marker-tiny.webp … marker-xxl.webp     generated by scripts/foundry/prompt-marker-art.py

  test/geometry-core.test.mjs              node --test fixtures for geometry-core
  README.md                                operator notes (one screen); the playbook is in context/
```

**Settings** (world scope unless noted, all with sane defaults so nothing needs configuring):

| Key | Default | Purpose |
|---|---|---|
| `panelRows` | 12 | side-panel rows before "+N more" |
| `panelChars` | 90 | description/prompt preview length in the panel |
| `gatherChars` | 160 | description preview length in the gather text |
| `unseenWithinFt` | 60 | how far away a walled/door-blocked neighbour is still listed |
| `cropsDefault` | `auto` | `auto` = crops on when exactly one scene is gathered; `on`; `off` |
| `cropMaxPerCall` | 6 | cap on crops per gather |
| `cropLongSidePx` | 768 | about 790 image tokens each |
| `deleteEmptyOnClose` | true | a *freshly dropped* marker closed with no text is removed |
| `defaultSize` (client) | `mid` | size placed by the `P` keybinding |
| `lastCalls` (hidden) | `[]` | ring of the last 5 gather manifests (see §6.4) |

**Keybindings:** `P` (configurable) = place a prompt marker of `defaultSize` under the cursor
and open the dialog; `Shift+P` while hovering a prompt marker = open its dialog. Dragging from
the sidebar remains the canonical path; the key is for the "twenty markers in a row" case.

### 1.2 The bridge fork: one new tool file

`~/Documents/GitHub/foundry-vtt-mcp` branch `pentaryn`:
`packages/mcp-server/src/fork/tools/prompt-markers.ts`, registered in `fork/index.ts` (one

`scripts/mcp/server.py` has no live client and the world DB is locked while Foundry runs. The

## 2. The six marker actors

Folder **`Prompt Markers`** (actor folder, sibling of `Markers (1–9)`; created by the module
on first GM ready). `ensureMarkers()` runs on every GM `ready`: creates missing actors, repairs
drifted fields (size, lock, art, flags), never deletes. Idempotent, logged once.

| Actor name | `traits.size` | Footprint (squares) | Space | Flag `marker` |
|---|---|---|---|---|
| `Prompt · tiny` | `tiny` | 0.5 × 0.5 | 2½ ft | `tiny` |
| `Prompt · small` | `sm` | 1 × 1 (texture scale 0.8) | 5 ft | `small` |
| `Prompt · mid` | `med` | 1 × 1 | 5 ft | `mid` |
| `Prompt · large` | `lg` | 2 × 2 | 10 ft | `large` |
| `Prompt · xl` | `huge` | 3 × 3 | 15 ft | `xl` |
| `Prompt · xxl` | `grg` | 4 × 4 | 20 ft | `xxl` |

Each is an `npc` actor with:

- `ownership.default: NONE` — never in a player's sidebar.
- `system.traits.size` as above **and** explicit `prototypeToken.width/height` **and**
  `prototypeToken.flags.dnd5e.lockSize: true`. The drop position is computed from the source
  width (`_getDropActorPosition`), so the prototype must already be right; lockSize is a native
  dnd5e flag and stops a later size edit on the actor from shifting placed markers.
- `prototypeToken.sight.enabled: false`, `disposition: SECRET`,
  `displayName: ALWAYS` (hidden tokens are invisible to players, so ALWAYS is GM-only in
  practice and gives a free nameplate — see §3.6), `texture.src` = the module's art.
- `flags.pentaryn-prompts.marker = "<size>"` on actor and prototype. **This flag, not the
  name, is how code recognises a prompt marker.**
- v14 prototypes have no `hidden`; a `preCreateToken` hook forces `hidden: true`,
  `sight.enabled: false`, and the lock on every token whose actor carries the flag.

**Art** (`scripts/foundry/prompt-marker-art.py`, PIL from `.venv`, 512×512 webp, run once and
committed under the module's `assets/`): a **rounded speech bubble with a quill** on a
transparent ground, a **dashed border at the image edge** so the whole footprint reads as a
box on the map, and the size word (`tiny` … `xxl`) in the bubble. One hue family for all six
(ink-violet `#5b3fa6` bubble, parchment `#f3e9d2` text) — the *shape* distinguishes them from the
colour set and the *label* from each other. Small and mid share a footprint, so small is also
drawn at `texture.scaleX/Y = 0.8` and its bubble is noticeably smaller. Empty markers are
tinted (`texture.tint = "#ff6b6b"`) until they have text; filled ones untinted.

## 3. The dialog

### 3.1 Opening on drop

1. `dropCanvasData` (synchronous, returns `undefined`): if `data.type === "Actor"` and the
   actor has the `marker` flag, remember `{actorId, clientX, clientY, t: Date.now()}`.
2. `createToken(doc, options, userId)`: when `userId === game.user.id`, the token's actor is a
   prompt marker, and a remembered drop matches (same actor, < 3 s old), open the dialog for
   that token at the remembered client position and clear the memory. Scripted creation (no
   matching drop) opens nothing; `game.pentaryn.prompts.open(tokenId)` is the explicit path.
3. The `P` keybinding creates the token itself (centred on `canvas.mousePosition`, snapped
   to the grid unless Shift is held) and opens the dialog directly.

### 3.2 Window

- `PromptDialog extends HandlebarsApplicationMixin(ApplicationV2)`, **not** `DialogV2`
  (DialogV2 closes on Escape without saving). `id: "pentaryn-prompts-dialog"` — one instance;
  opening a second marker re-targets it after saving the first.
- Default size **620 × 320 px**, resizable, minimisable off. Two columns: **side panel 240 px
  left**, textarea fills the rest. Footer under the textarea: size chips `tiny small mid large
  xl xxl` (current one highlighted), `Delete`, and a muted hint `Esc saves · ⌘⏎ saves`.
- **Position:** top-left at `(clientX + 24, clientY − 40)` of the drop/click; clamped so the
  whole window stays on screen; never over the marker itself when it can be avoided (if the
  marker would be covered, flip to the left of the cursor). Reopening uses
  `canvas.clientCoordinatesFromCanvas(markerCentre)`.
- **Focus:** `autofocus` on the textarea plus `requestAnimationFrame(() => ta.focus())` on
  render. Caret at the end of existing text.

### 3.3 Keys (listener on the dialog root, keydown, runs before core's window listener)

| Key | Behaviour |
|---|---|
| **Enter** | Newline (native textarea; nothing intercepts it) |
| **Esc** | `preventDefault` + `stopPropagation`, **save, close** |
| **⌘⏎ / Ctrl+⏎** | Save, close (hands-on-keyboard alternative) |
| **Shift+Esc** | Discard unsaved edits, close (restores last saved text) |
| **Shift+Tab / Tab** | Normal focus traversal into the panel and chips |
| Everything else | Textarea default; core keybindings are already skipped while a TEXTAREA has focus |

Core's dismiss closes *every* framed window with `close({closeKey: true})` when focus is
outside any window, so **`close()` itself saves** regardless of the path that led to it.

### 3.4 Saving

- Text lives on the **token**: `flags.pentaryn-prompts.prompt` (string, trimmed, `\n`
  paragraphs preserved) and `flags.pentaryn-prompts.updatedAt` (ms epoch).
- Autosave while typing, debounced 600 ms, plus on close. An update is skipped when the text
  is unchanged. Saving never moves focus or re-renders the textarea.
- Saving also sets the token **`name`** to the nameplate form (§3.6) and clears/sets the empty tint.
- **Empty on close:** if the marker was *created by this drop* (the dialog was opened by §3.1
  step 1-3, not reopened) and the text is empty, the token is deleted and a 2 s toast says
  "Prompt marker removed (empty)". A reopened marker emptied by hand is kept, tinted, named
  `Prompt · mid — empty`. `deleteEmptyOnClose: false` turns the deletion off.
- **Size chips:** choosing another size replaces the token with the matching marker actor,
  **centred on the old centre**, carrying the text, in one create + one delete; the dialog
  re-targets the new token id. (Different actor ids are what make the footprint reliable, so
  resizing is a swap, not an update.)

### 3.5 Reopening to edit

- **Double-click** the marker: libWrapper `MIXED` on
  `foundry.canvas.placeables.Token.prototype._onClickLeft2`; for a prompt marker open the
  dialog instead of the sheet. Without libWrapper the method is wrapped by hand (store the
  original, call through) — same effect, declared so in the README.
- **Token HUD** button (`renderTokenHUD`): a bubble icon, "Edit prompt".
- `Shift+P` while hovering; `game.pentaryn.prompts.open(tokenId)`.
- `Delete` key on a selected marker works as for any token — no prompt text is ever stored
  anywhere else, so deleting a marker is final (the gather text, if one was run, still has it).

### 3.6 Showing that a marker has text

- **Nameplate (native, `displayName: ALWAYS`):** `✎ <first 40 chars of the first line>…`;
  empty → `Prompt · mid — empty`. GM-only in practice because the token is hidden.
- **Tooltip on hover** (`hoverToken` → `game.tooltip.activate`): the full prompt, the size, and
  the in-sight count, `pentaryn-prompts-tip` styled, up to 600 chars then "…".
- **Empty tint** red until text exists.

### 3.7 The side panel — "what this marker can see"

Computed on open from the scene *documents* through the same `model.mjs` the gather uses, so
the panel and Claude's context can never disagree. Under 50 ms for a 70-token scene; computed
fresh on each open (no live tracking).

Rows, **nearest first** (nearest-square distance, then id), **LOS-filtered**: only things the
marker can see with unlimited darkvision through the scene's walls (light ignored, doors as
they currently stand — closed blocks, open passes):

| Row kind | Image | Line 1 | Line 2 | Line 3 |
|---|---|---|---|---|
| other prompt marker | bubble glyph with its size word | `Prompt · large` | `20 ft · close · NE` | first `panelChars` of its text, or *(empty)* in italics |
| built token (NPC/PC/creature) | token image 32 px (ring subject texture when ringed) | name | `15 ft · close · N · hidden?` | biography preview, or `Built from: "<prompt>"` if it has provenance and no biography |
| item pile / hotspot | token image | name | distance line | `flags.item-piles.data.description` preview |
| journal note | pin icon | note label / page name | distance line | page text preview |
| light with provenance | lamp glyph | `Light` | distance line | its provenance prompt |

- Rows: `panelRows` (12), then a `+N more` line that expands.
- A collapsed **"Out of sight (within 60 ft)"** section lists neighbours blocked by a **door**
  (tag `door`) or **wall** (tag `wall`), greyed. This is how Joe sees the leader behind the
  door he is about to put a guard in front of.
- Excluded: colour/number markers (scaffolding), tokens of the marker actors' *own* id, the
  marker itself, and `Temp`/`Markers` folder actors.
- Clicking a row pans the canvas to it (`canvas.animatePan`) without closing the dialog;
  ⌘-click opens its sheet/dialog.
- Heading: `In sight · 7` with the map size `150 × 100 ft` beside it for perspective.

## 4. Geometry: distance, sight, grouping

All in `geometry-core.mjs` (pure) and `los.mjs` (Foundry collision), shared by the panel and
the gather. Works on scenes nobody is viewing (v14 keeps edges on the Level document).

### 4.1 Distance (5e, grid)

- Occupied squares from `TokenDocument#getOccupiedGridSpaceOffsets()` (dedupe on `i,j`).
- **Distance = `scene.grid.measurePath([nearestA, nearestB]).distance`** over the nearest pair
  of occupied squares. Adjacent = 5 ft. Uses the world's diagonal rule
  (`core.gridDiagonals = 0`, every diagonal 5 ft, the 2024 default).
- Notes and lights occupy the single square under their centre.
- Gridless scenes: edge-to-edge euclidean, rounded up to 5 ft.
- Also reported: **bearing** (8-point compass, north = up, from centre to centre) and the
  position in feet from the *map's* top-left (canvas minus padding; `markers.md` conversion).

### 4.2 Bands — fixed, 5e-anchored (2024 PHB, checked through `game.pentaryn.rules`)

| Band | Feet | Anchor |
|---|---|---|
| `touching` | 5 | melee reach, grapple, Help |
| `reach` | 10 | Reach property (+5 ft); Large+ monster reach |
| `close` | 15–30 | one move at speed 30; 30-ft spells (50 in the PHB); thrown 20/30; 15-ft cones |
| `near` | 35–60 | move + Dash; 60 ft is the commonest spell range (72 spells); Darkvision 60 |
| `far` | 65–150 | 90/120/150-ft spells (71 together); shortbow 80, heavy crossbow 100, longbow 150 |
| `distant` | 155+ | long ranges only; same map, separate encounter |

### 4.3 Line of sight

`CONFIG.Canvas.polygonBackends.sight.testCollision(origin, dest, {type: "sight", mode: "any",
level, useThreshold: true, edgeTypes: {source: false}})` with `level =
scene.levels.get(token.level) ?? scene.firstLevel`, origin `getMovementOrigin()`, targets
`getVisibilityTestPoints()`; visible if any target point is clear. Core handles open doors,
one-way walls, limited walls (second hit blocks), proximity thresholds. `edgeTypes.source:
false` removes darkness edges — light is irrelevant. Multi-level scenes also run
`scene.testSurfaceCollision`. 2,278 pairs on Fighting Pit took 139 ms unviewed.

**Second pass** for blocked pairs only: a custom ray over `level.edges.getEdges(rect)` that
skips door edges (`door !== NONE`). Clear there → class `door` (secret doors tagged `secret`),
else `wall`. Each pair is therefore `LOS | door | wall`.

Levels / wall-height: active but unused (every scene has one level, no wall heights). A TODO
hook point in `los.mjs` filters edges by elevation if that ever changes.

### 4.4 Grouping

- **Encounter:** single-linkage components over edges `≤ 30 ft AND LOS`, among prompt markers
  and built tokens. **A built token may join but may not bridge**: edges are first formed among
  prompts; a built token attaches to every prompt component it links to and, if that is more
  than one, it is listed in each as `shared` rather than merging them.
- **Formation:** the same at `≤ 15 ft AND LOS`, inside an encounter.
- **Alone:** an encounter of one prompt. Its `door`/`wall` neighbours within `unseenWithinFt`
  are still listed, so "behind a closed door 20 ft from the pack" is said outright.
- **Ids** (deterministic for the same board): scenes `s#` in `game.scenes` nav order then
  name; encounters `E#` per scene by member count desc, then top-left reading order; prompts
  `p#` by scene, encounter, marker size desc, then reading order (`y`, then `x`); built `t#`
  likewise. Same board → same ids → the same `call` id (`pm-` + 4 hex of a hash over scene ids,
  marker ids and prompt texts).

## 5. The one-call context export

### 5.1 Scope and knobs

`gather({scenes, crops, chars, unseenWithinFt, builtWithoutProvenance})`

- `scenes`: `"all"` (default: every scene that has at least one prompt marker, in nav order),
  `"current"`, or a list of scene ids/names.
- `crops`: `"auto"` (default; on when exactly one scene is gathered) | `true` | `false`.
- `builtWithoutProvenance`: `true` (default) — hand-built tokens are context too.
- Over ~40 prompts the text reaches ~6k tokens; Claude Code's MCP output cap (believed ~25k,
  `MAX_MCP_OUTPUT_TOKENS`) is far off. The tool still pages: `maxPrompts: 60` per call with a
  `next` scene id, and the playbook says to gather scene-by-scene for monster boards.

### 5.2 Returned shape (query result)

```ts
{ call: "pm-7f3a", text: "<prompt_markers …>…</prompt_markers>",   // §5.3, what Claude reads
  counts: {scenes, prompts, built, encounters, alone},
  manifest: Manifest,                                                 // §6.4, machine side
  crops: [{encounter: "E1", scene: "s1", png?: base64webp, path?: string, squares: "12x9"}],
  next: null | "<sceneId>" }
```

The MCP tool returns `text` as the first content block, each crop as an **image content block**
(after the `backend.ts` passthrough edit in §10), and a short trailing text block with the
`call` id and counts. The manifest is stored, not returned (the model never needs 16-char ids).

### 5.3 The text — Draft A, in full

Research outcome: structure beats syntax; group hierarchically, state relations locally, put
data first and the task last; short ids; give feet *and* a band; nearest-first. The toy example
costs 1.9k tokens in this layout against 3.7k flat JSON with the same information, and reads
better because each text appears once and the encounter is the unit Claude designs.

```
Built from prompt (tiny, 2026-10-02): "notice board with three jobs on it"
Description: A warped board of wanted posters and lost-dog notices...
</built>
</context_only>
</scene>

<todo>p1 p2 p3 p4 p5 p6 p7 p8 p9 p10 p11 p12</todo>
</prompt_markers>
```

Rules the renderer follows:

- Every prompt's and built thing's text appears **once**, inside its own element; relation lines
  carry only ids, feet, bearing, band and `door`/`wall` tags.
- `<sees>` lists everything with LOS, nearest-first, no cap (a prompt rarely sees more than 15
  things; if it sees more than 25, the rest are summarised as `+N more beyond 60 ft`).
- `<unseen>` lists `door`/`wall` neighbours within `unseenWithinFt`, nearest-first.
- `kind` for built things: `npc | character | creature | hotspot (item pile) | note | light |
  tile`. `hidden="yes"` when the token is hidden. Built things with no provenance omit the
  "Built from prompt" line.
- Regions: the names of Region documents whose shape contains the item's centre.
- `nav` = `scene.navName` when set. The scene description (if any) is appended to `<overview>`
  as `Scene notes: …` truncated to 300 chars.
- Prompt text is emitted verbatim (newlines kept), after HTML-stripping if any.

### 5.4 Image crops

**Decision: on by default when exactly one scene is gathered, opt-in for batches, max 6 per
call, one per encounter (not for loners), long side 768 px (~790 tokens each).**

Rendered in the GM's browser with an `OffscreenCanvas` from the level's background image
(loads in ~12 ms; 1.2 s per crop including encode), no scene switch, no PIXI: crop = encounter
bounding box + 15 ft margin (min 8 squares); draw token art (ring subject texture when
present), **footprint boxes labelled `p#`/`t#` in the same ids as the text**, wall lines (doors
dashed), a 5-ft scale bar and a north arrow. WebP (~110 KB). The legend warns the model that
the picture is set dressing only. Cost for a typical scene: 3–5k tokens, about equal to the
text — Joe ranks quality above tokens, and the picture is what tells "altar" from "bar".

### 5.5 Exposure

- **Module API:** `game.pentaryn.prompts.gather(opts)` → the §5.2 object (crops as base64).
  `.list()`, `.replace(spec)`, `.replaceMany(specs, {dryRun})`, `.open(tokenId)`,
  `.ensureMarkers()`, `.model(sceneId)` (debug: the raw geometry).
- **Queries** (`CONFIG.queries`, GM-guarded on `ctx.user`): `pentaryn-prompts.list`,
  `.gather`, `.replace`, `.crops`.
- **MCP tool** `prompt-markers` (fork, one fat tool, `action` enum per fork principle 5):
  - `action: "list"` — scenes with prompt counts, empties flagged.
  - `action: "gather"` — §5.1 knobs. The one call.
  - `action: "crops"` — `{call, encounters: ["E1", …]}`, re-request or add crops after a gather.
  - `action: "replace"` — `{call, replacements: [...], dryRun}` (§6). Registered `{write: true}`.
  - `action: "show"` — `{call, id: "p3"}` pans the GM canvas to that marker (switching scene if

## 6. Replace helpers

### 6.1 Spec

```ts
type Replacement = {
  // which marker — by gather id (preferred) or directly
  call?: string; id?: "p3";
  sceneId?: string; markerId?: string;
  with: With;
  name?: string;            // token/pin label override
  hidden?: boolean;         // default: creatures false, lights n/a, notes n/a
  note?: string;            // free text copied into provenance.note (why this choice)
};

type With =
  | { kind: "actor";   actorId?: string; uuid?: string /* world or compendium */; copy?: boolean }
  | { kind: "npc";     npc: Dnd5eCreateNpcArgs; features?: Dnd5eAddFeatureArgs[] }
  | { kind: "hotspot"; name: string; description: string; items?: {uuid: string, quantity?: number}[];
                       size?: number /* grid units, default 0.5 */; locked?: boolean; icon?: string }
  | { kind: "note";    name: string; html: string; folderId?: string; label?: string;
                       ownership?: "observer" | "none" | {[userId]: level}; iconSize?: number; icon?: string }
  | { kind: "light";   config: AmbientLightData["config"]; hidden?: boolean }
  | { kind: "tile";    src: string; width?: number; height?: number /* grid units */ }
  | { kind: "none";    reason: string };      // nothing goes here: delete the marker, keep the text in the readback
```

`npc` uses the bridge's existing `foundry-mcp-bridge.createNpcActor` query (the engine behind
`dnd5e-create-npc`) and then `dnd5e-add-feature` for each `features` entry, server-side,
before placing. `hotspot` clones `Hotspot · Look (template)` exactly as `markers.md` does (all
four item-piles images, `deleteWhenEmpty: false`, `distance` unset, lockSize for 0.5).
`note` follows the readable recipe (`ownership.default: OBSERVER` unless told otherwise,
`global: false`, eye icon, `iconSize` 64 ≈ 0.5 square). `actor` with `uuid` of a compendium
entry imports it into `Foundry MCP Creatures` first (`copy: true` default for compendium,
`false` for world actors — place the existing actor).

### 6.2 Placement contract

| Case | Position |
|---|---|
| Creature whose footprint equals the marker's | the marker's own `x, y` (top-left) — exact squares |
| Creature with a different footprint | centred on the marker's centre, snapped to the grid |
| Hotspot, tile | centred on the marker's centre (not snapped — hotspots sit on the object) |
| Note, light | `x, y` = marker centre (these documents are centred) |

- `flags.dnd5e.lockSize: true` on the placed token whenever its width ≠ its actor's size
  category width (hotspots, tiles-as-tokens, odd sizes).
- `hidden` set **explicitly** on the placed token (prototype hidden does not survive
  `getTokenDocument`).
- Elevation copied from the marker.

### 6.3 Provenance

Stamped on **every** document the replacement creates:

```js
flags["pentaryn-prompts"].provenance = {
  prompt: "<the full text>", size: "mid", footprint: "1x1",
  sceneId, markerId, call: "pm-7f3a", pid: "p3",
  at: 1760140800000, kind: "npc", note: "<Replacement.note>" }
```

On the Token (and AmbientLight / Note / Tile) and, for `npc` / `hotspot` / `note`, also on the
created Actor / JournalEntry so it survives the token being deleted and re-placed. Gather reads
provenance from the placed document first, then its actor/entry.

### 6.4 Manifest, hash check, batch, dry-run, readback

- The gather stores `Manifest = {call, at, prompts: {p1: {sceneId, markerId, size, hash,
  x, y, w, h}, …}, scenes: {s1: sceneId, …}}` in the hidden world setting `lastCalls` (ring of
  5). `replace` by `call`+`id` re-reads the live marker, refuses with `TEXT_CHANGED` if its text
  hash differs (Joe edited it after the gather — regather), `MARKER_GONE` if it no longer
  exists, and `CALL_UNKNOWN` if the ring has rotated it out (fall back to `sceneId`+`markerId`).
  `force: true` overrides `TEXT_CHANGED` only.
- **Batch:** replacements are grouped by scene; per scene one `createEmbeddedDocuments` per
  document type (Token, Note, AmbientLight, Tile), then one `deleteEmbeddedDocuments("Token",
  markerIds)`. Actors/journals are created first in one batch. A failure in one replacement
  does not delete *its* marker; the rest proceed. Nothing is deleted before its replacement
  exists.
- **Dry run** (`dryRun: true`): returns the plan — per replacement the resolved marker, the
  footprint, the computed `x, y`, lockSize, hidden, and the documents that would be created —
  with no writes. The playbook requires a dry run before any batch over 5.
- **Readback** (always): per replacement `{id, ok, created: [{type, id, name, x, y, w, h}],
  deletedMarker: true|false, error?}` read back from the scene after the writes, plus
  `remaining: <prompt markers still on the scene>`.

## 10. Risks, edits to upstream, and findings to act on

- **10 s query timeout** (`foundry-connector.ts:382`) silently caps everything, including
  `eval-js`'s advertised 60 s. Gather with 6 crops is ~8 s; the per-query `timeoutMs` edit is
  required, not optional.
- **Results are one text block** (`backend.ts:1775-1782`). Image passthrough is a 6-line edit
  behind an `Array.isArray(result?.__mcpContent)` check; keep the file fallback.
- **Security:** the fork's `foundry-mcp-bridge.fork.eval` only checks `game.user.isGM` on the
  *running* client; the default player role holds `QUERY_USER`, so a player could run JS on the
  GM's browser via `game.users.activeGM.query(...)`. Fix in Unit B: reject when `ctx?.user` is
  present and not a GM — and apply the same guard to every `pentaryn-prompts.*` handler from
  day one.
- **Two GM tabs double every hook** — including the dialog-open and the autosave. The
  single-instance dialog id makes a double open harmless, but the rule stands: one GM client.
- **`markers.md` is stale on three points** (folder `Markers (1–9)`, no colour set in this
  world, Alt hides / Shift unsnaps in v14, markers are not prototype-hidden). Fix with Unit B.
- **Levels / wall-height** are installed and unused; `los.mjs` has the elevation filter hook
  point but does not implement it. If a scene ever gains heights, the LOS is wrong silently —
  the gather prints `levels="n"` and a `WARN wall heights present, LOS ignores them` line so
  it is at least visible.
- **Crop art for ringed tokens** uses the ring subject texture; dynamic-ring colours are not
  reproduced. Acceptable: the label carries the id.
- **Joe's number markers remain** for pointing; prompt markers are not a replacement for
  "the red one is a chest" when the thing is already decided.

## 11. Eval round 1 (2026-10-10) — what changed and why

The first LLM evaluation (13 prompts on two scratch boards, scored context 7 / result 8 /
efficiency 5) found the format sound and the build path thin: the tool was missing from the
builder's session, 7 of 13 prompts were "stock monster plus changes" and 4 were level-5 PCs, both

- **Tool availability.** Claude Code caches `tools/list` per session; a session started before

  `tools.listChanged` and polls the backend's list every 30 s, sending

- **Gather format.** `<built>` prints the provenance `note` (`Why:`) and `pN of pm-xxxx`;
  descriptions run to 400 chars cut at a sentence (`previewSentences`); empty `<unseen>` says so;
  loners name the nearest built thing they can see; door lines per door near a prompt
  (state, wall orientation, groups per side); encounter relations say what blocks them;
  `elev` on anything off the ground; an XP budget line per scene and built XP per encounter when a
  `party` is given (world setting or argument).
- **Build helpers.** `actor` + `patch` (`patch.mjs`: rename, size, bio, hp/ac/cr/speed, remove /
  add items by name or inline data, monster traits with activation/recharge/uses, recharge on
  existing items, escape hatches). `character` (`character.mjs` + pure `build-core.mjs`): PHB
  class/subclass/species/background run through dnd5e's AdvancementManager steps headlessly,
  ability budget validated, every unstated choice defaulted *and reported*. Inline `{data}` items
  for hotspots and patches, so no world items escape cleanup. Replacement-level `ring`, `img`,
  `disposition`.
- **Readback.** `markerDeleted` (true/false), per-replacement `report` (patch list; a character's
  sheet numbers, defaults, warnings), and per-encounter XP vs the party budget.
- **Crops on the eval path** are uploaded to `Data/pentaryn-prompts-crops/<call>/` and returned as
  paths (`cropsAs: "files"`, the API default); the bridge's queries still get base64 → images.
- **Rules.** `pentaryn-lookup` gains `onList` / `spellList` (dnd5e's spell-list registry — the
  PHB's list pages are empty) and returns a page's embedded roll tables; `dnd5e-add-feature`
  takes `recharge`; `rules-lookup.md` has the dnd5e 6 notes (activity damage parts merge the base
  die on read; spell `method` / `prepared` 0|1|2; recharge shape; the species-link race).
- **Not changed:** `create-actor-from-compendium` already files into `Foundry MCP Creatures`
  (verified live); the eval's claim otherwise did not reproduce.

## 13. Eval round 2 fixes — module 0.3.0 (2026-10-10)

The Fable judge scored round 2 context 8 / results 8 / efficiency 7 and listed six items; all six
are in module 0.3.0 and the fork, built and tested, **not yet deployed** (sync the module and restart
the broker together: the fork now passes `npc` through, which 0.2.0 cannot build).

**1. Built things join encounters (the important one).** Joe drops new prompts beside things
already built, so a prompt within 30 ft + LOS of a built creature is no longer "Alone".
Design, in `groupScene` / `assignIds`:

- *Packs.* A **hostile** built creature (npc, character, plain actor token — not hotspot, note,
  light, tile) that joins a prompt group brings its **pack**: the hostile built creatures chained to
  it at ≤ 30 ft with LOS, found breadth-first from the foes that linked directly. So `p1` beside
  `t6 Pell` gets `t4 Skrag, t5 Grek, t7 Snikka` too, which is the fight the new minion belongs to.
  Neutral and friendly creatures never chain (§13.1: the build shipped "same disposition", which
  chained neutral street crowds — up to 18 tokens on the Molten Ward), so the hostile camp does not
  pull in the neutral innkeeper and a crowd joins only where it stands within 30 ft of a prompt.
  Objects never chain: a chest joins only when it is itself within 30 ft of a prompt.
- *One prompt + a hostile built creature = an encounter.* One prompt beside built objects or
  non-hostile creatures only stays "Alone", and those stay context — a chest or a villager is not a
  fight (the loner line names the nearest one).
- *Built things still never bridge two prompt groups* — decided, not inherited. A pack reached from
  two groups is attached to both and listed as `Shared with E2: … (built things never merge
  encounters; decide whether this is one fight)`, with `(shared XP counted in each)` on the XP.
  Reasons: one built guard in a corridor between two rooms must not fuse two rooms' fights into one
  encounter (the original case for the rule); a merge driven by built tokens would make ids and the
  crop of an encounter swing with whatever was built last; and the case where it *is* one fight is
  the rarer one and is now named outright, so the builder decides with the facts in front of it.
- The encounter line names built members and their XP whether or not a party is given:
  `E1: p1 + built t1 "Skrag", t2 "Grek", t3 "Pell", t4 "Snikka". Built XP already in it: 350.`
  The replace readback's per-encounter XP already counted built members (manifest).
- Cost: pack edges are distance-first and cached; sight is only tested for creature pairs within
  30 ft, and only for packs a prompt actually reaches.

**2. Fallback parity.** `npc` is built in the module (`npc.mjs`, pure `npc-core.mjs`) through the
bridge module's own `CONFIG.queries["foundry-mcp-bridge.createNpcActor" | ".add…ToActor"]`
handlers, with the tools' zod checks and defaults restated (sourceRules "2014", spells from
`dnd5e.spells`, as the tools default) plus unknown-key refusal; so it dry-runs field by field and
works through eval-js. The actor is the run's (deleted if its replacement fails later); a duplicate
NPC name is allowed (temporary name, renamed). `replaceMany` returns flat rows
(`readback-core.mjs`: strings, numbers, booleans, lists of strings) and `text`, the readback; the fork
prints that `text` verbatim, so both paths read back the same lines (sheet:, DEFAULTED, patched:,
notes:, cleanup:, remaining:, encounter XP). A suite test runs a full result through a restatement
of the bridge's eval-js serialiser and finds no `[max depth]`. The fork lost its npc expansion and
its own render (a module without `text` is named and its raw result printed).

**3. The dry run validates what the real run would.** `character.choices` keys against the
advancements the build steps through (species, background, class levels 1..N, subclass, their
`ItemGrant`s, and items the choices themselves name — a Versatile feat, a Fighting Style, an ASI
feat), unknown → `BAD_SPEC` with the known keys and the nearest; checked live against PHB
Paladin 5 / Human / Soldier (§13.1: the claim that every key of the playbook example was recognised was wrong — its Magic Initiate keys are unknown with `"Versatile": "Tough"`; the example was fixed and resolved live). `spells` /
`spellbook` found and on the class list; `items`, class, species, background found, a miss naming
the nearest PHB names (`Spellbook` → `Book`; `Elf` → the `Elf, …` lineages; the world has no plain
`Elf`). Languages: an unanswered language Trait takes the species' tongue, then Common and the
common ones (sign language last), printed `DEFAULTED`; npc and patch language words become dnd5e
keys (`common`, `goblin`); `patch.creatureType` (new) and a `set` of the type clear inherited
languages unless `patch.languages` (new) says otherwise; inline `{data}` items whose text requires
attunement get `system.attunement: "required"` (printed `DEFAULTED`). Character `items` take `{data}`.

**4. Richer `<built>`.** `type` (a character: `Paladin 5, Oath of Devotion (Human)`), `stats`
(`CR 1/4, AC 15, HP 11`, `HP 7/11` hurt), `disposition`, a hotspot's `Items:` (rarity,
`unidentified, shows as "…"`, attunement, price) and a creature's notable `Carries:` (loot,
consumables, containers, tools, anything magic). CR moved out of `type` into `stats`.

**5. Door lines.** A group goes on a side only through a member with a sight line to a spot just
