# Pentaryn Pins — design (2026-10)

**Read this when:** you are building or reviewing pinning, the GM right-click canvas menu, or the
portals `teleportToken` entry point, or you want to know why they are shaped this way. This is
history. Once shipped, the use-doc is `context/foundry/pins.md`. Run the generator **without
`--docs`**. With `--docs`, it would write a second, empty plan at `context/plans/pins-2026-10.md`
beside this one. This file is the plan; write the use-doc by hand (step 10).

## Goal (Joe, 2026-10-17)

Joe runs one character per login. He moves a player's view by moving that character's token, never
by copying it. He wants a **world switch** that, when on:

- keeps each pinned player on **whatever scene their pinned token is on**, and ignores GM scene
  activation for them, because activating a scene must not jump everyone;
- shows "Pinned to {player}" on the character sheet;
- gives the GM a right-click menu on empty canvas with **Prompt note** (the same action as P) and
  **Teleport pinned character ▸ {logged-in player}**, which moves that player's character to the
  clicked point;
- brings the character's summons, pets and connected tokens along on that teleport, exactly as
  portal travel already does. **This is a hard no-regression requirement.**

A pin binds an Actor to a User. Pins are set and cleared only through the API or bridge, with no
edit UI. Turning the switch on audits that each pinned actor has exactly one token across all
scenes. A token counts as the pinned actor's when its **root actor** is the pin: the token's own
actor, or, while the character is wild-shaped or polymorphed, the original actor that dnd5e records
in `flags.dnd5e.originalActor` (D3).

### Topology correction (task premise)

The task says the active GM is the headless bot "Claude". That holds only when no role-4 GM is
connected. While Joe's browser is open, **Joe's tab is `game.users.activeGM`**: `activeGM` is
`getDesignatedUser` by highest role, so Joe's role-4 tab outranks the role-3 bot
(`context/foundry/headless-gm.md` §activeGM; verified in review). Portal-hop follow (`party.mjs`
`onDeleteToken`) then runs in Joe's browser. This design does not depend on either answer:

- `teleportToken` runs on whichever GM client calls it: Joe's tab for the menu, the bot for
  `pentaryn-write`.
- The scene-follow logic runs on each pinned **player's** own client.
- The bot runs without a canvas, so nothing in pins may need `canvas` on a GM path the bridge calls.
  `teleport` takes its scene, point and level as arguments.

Also verified in review, and relied on below: pins' `ready` runs before resume's, because pins
registers `Hooks.once("ready")` when its entry script evaluates and resume registers its listener in
`setup`. Core TeleportToken ignores `displace` moves (`client/data/region-behaviors/teleport-token.mjs:77`),
so a same-scene `teleportToken` onto a portal square cannot chain-teleport.

## 1. pentaryn-portals: `teleportToken` (built first)

### API row (own row, appended after `unlink` in `MANIFEST.rows`)

```js
{
  path: "teleportToken",
  params: [
    { name: "ref", kind: "token", type: "Token|uuid|id|exact name",
      doc: "the token to move (a PC brings its company); opts.sceneId scopes an id or a name" },
    { name: "opts", type: "{ x, y, scene?, level?, dryRun = false, sceneId? }",
      doc: "x, y: canvas point on the destination where the token's centre should land; scene: destination scene id|uuid, default the token's own scene; level: destination level id (v14), default the token's level on the same scene, the destination's initial level (else its first) on another" },
  ],
  returns: "{ ok: true, token, from, to: { scene, x, y, level }, followers: [{ id, name }], moved, dryRun? } | { ok: false, code, reason }",
  gm: true, writes: true, dryRun: true, since: "0.6.0",
  sideEffects: ["Token: x, y, level — same scene, one update with displace waypoints that carry the level, no animation",
    "Token: create keepId on the destination + plain delete on the source — another scene (no replacements; combatants are not remapped)"],
  doc: "Move one token and, when it is a PC (character or polymorphed), its company (its summons, tokens only its players own) to a point, on its own scene or another. Same follower rule as portal travel, without the portal check. No confirm; nobody is pulled; no view changes. Each follower lands beside the PC.",
}
```

`opts.sceneId` stays reserved for scoping the ref (`lib/resolve.mjs:45-52`). The destination is
`opts.scene`. `to.scene` and `to.level` in the return are **id strings**.

### Implementation

The **row impl** lives in `api.mjs`, like `link`/`unlink` (`api.mjs:62-95`): argument checks,
`fail`/`ok`, `dryRun`, the audit log through `ctx`. It is wired in `buildApiFor` as
`teleportToken: (token, opts = {}) => teleportToken(token, ctx, opts ?? {})`. The **gathering and
moving** live in `scene-adapter.mjs` as `export async function moveCompany(token, dest, { x, y, level }, { dryRun })`,
next to `teleportParty`. The adapter gets log and setting through `configureSceneAdapter`, never
`ctx` (its header says so).

`api.mjs` `teleportToken(token, ctx, opts)`:

1. `fail("NOT_GM")` unless `game.user.isGM`.
2. `from = token.parent`. `dest = opts.scene ? game.scenes.get(id) ?? fromUuidSync(uuid) : from`.
   A miss returns `fail("NOT_FOUND")`. A non-finite `x` or `y`, or a `level` the destination does
   not have (`!dest.levels.has(level)`), returns `fail("BAD_ARGS")`.
3. **Resolve the level explicitly**:
   `level = opts.level ?? (dest === from ? token.level : dest.initialLevel?.id ?? dest.firstLevel?.id ?? null)`
   (`common/documents/scene.mjs:252,265`). A bridge call without a level to a multi-level scene
   therefore never carries a source-scene level id across.
4. Call `moveCompany`, which does steps 5-9, then audit-log `ctx.log.info("teleportToken", { uuid, ids, by: game.user.id })`
   (§5.1) and return `ok({...})`. No toast; the caller toasts.

`scene-adapter.mjs` `moveCompany`:

5. `gmIds = gmUserIds()` and `lead = recordOf(token, { gmIds })`. The leader rule is
   `lead.type === "character" || lead.polymorphed`, the same rule as `party.mjs` `bringFollowers`.
   For a non-PC the company is `[]` and the token moves alone. That is not an error.
6. **Gather the company before anything moves**:
   `company = followersOf([lead], from.tokens.filter(t => t.id !== token.id).map(t => recordOf(t, { gmIds })))`.
   Then `party = [lead, ...company]` and `toks = party.map(r => r.doc)`.
   `dryRun` returns `{ followers, moved: 0 }` here and writes nothing.
7. **Same scene:** `places = landingPlaces(dest, toks, x, y, party)`, then one
   `from.updateEmbeddedDocuments("Token", updates, displaceToLevel(updates, level))`, where each
   update also carries `level`. `displaceToLevel` is a **teleportToken-local** builder in
   `portals-core.mjs` that returns `displaceOptions`' shape with `level` **in every waypoint**:
   `{ animate: false, movement: { [_id]: { waypoints: [{ x, y, level, action: "displace" }] } } }`.
   This matters: with explicit waypoints, core takes the movement fields from them
   (`client/documents/token.mjs` `#preUpdateMovement`, `:1693-1760`) and fills a missing
   `waypoint.level` with the previous level (`token.mjs:2310`), so a `level` only in the update
   would be dropped and the PC would land on the old floor. `displaceOptions` itself is unchanged,
   for `party.mjs:77` and `teleportParty`.
8. **Another scene:** `await carryTo(toks, dest, x, y, party, { level })`. **carryTo gains an
   optional trailing `{ level } = {}`** that, when defined, overrides `level` in the created data.
   Every existing caller (`bringFollowers`, `teleportParty`) passes nothing, so its data stays
   byte-identical, including `teleportParty`'s known source-level carry (Risks).
   **Superseded (portals 0.6.0, live 2026-10-17):** carryTo no longer copies the source level. Without
   `{ level }` it picks one the destination has (`preferLevel`, else the token's own id when shared, else the
   initial level) and maps elevation onto it (`arrivals()`; Risks, Levels).
9. An `already exists` error from the keepId create returns `fail("CONFLICT", "another session moved it first")`.
   This is the same election that `bringFollowers` relies on. Any other error rethrows to `api.mjs`,
   which logs it and returns `toFail(err)`.

There is no `canvas`, no `pullUsers` and no `dest.view()`. Pinning moves the player's view, and the
bot has no canvas. carryTo's delete has no `replacements`, so the follow hook never fires a second
time (`party.mjs` `onDeleteToken` returns on its first line). The flip side is that core's combat
remap (`client/documents/combat.mjs:1179`) only follows `replacements`: a cross-scene teleport mid
combat drops the PC and its company from the tracker (Known gaps; `teleportParty` already has it).

### Client mechanism (`follow.mjs`): which scene a pinned client shows

Installed in `setup`. That is after settings, users, actors and scenes are loaded, and before
`Game#initializeCanvas` draws anything. Everything is a pass-through unless `setting("pinning")` is
on, `!game.user.isGM`, and `pickToken` returns a token. With the switch off, unpinned, or no token,
the wrapper calls `wrapped` with the same `this` and args, including core's own loading toast: stock,
byte for byte.

**The view queue.** One per client, in `follow.mjs`. All of pins' own views go through
`request(want, reason, viewOptions)`, never straight to `Scene#view`:

- `inflight`: the `{ scene, level }` of the draw the wrapper last let through, set just before it
  calls `wrapped` and cleared in its `finally`. Every `Scene#view` on a pinned client passes the
  wrapper, so pins knows the target of every view-started draw.
- `request` asks `queueDecision`. `view` → `scene.view({ ...viewOptions, level })`. `none` → nothing.
  `defer` → store `want` as `pending` and start `settle()`.
- `settle()`: one `setTimeout` poll at 100 ms (at most one loop alive, given up after 120 s with a
  `log.warn`). When `canvas.loading` is false it **recomputes the target fresh** from `pickToken`
  (never the stale `pending`) and calls `request` again. It never runs inside a `canvasReady` call.
  `uninstall()` clears the timer.

**Patch `pins-scene-view`.**
`wrapMethod(MODULE, { target: CONFIG.Scene.documentClass.prototype, name: "view", marker: "__pentarynPinsView", adjustments: "pins-scene-view" }, …, { via: libWrapperRoute() })`,
MIXED. On the pinned path:

1. `viewDecision` gives the wanted `{ scene, level }`: `this` and the asked level on a pass, the
   token's scene and level on a redirect.
2. **If `canvas.loading`**: `queueDecision` with that want. `none` (the wanted scene is already being
   drawn — the usual case for a pull that arrives after `createToken: follow` started the draw) →
   return `this` **without calling `wrapped`**, silently. `defer` → hold it as `pending`, start
   `settle()`, return `this`. Core's guard and its "You cannot switch Scenes until resources finish
   loading" toast are never reached on the pinned path.
3. Not loading, `redirect`: do not call `wrapped`; return `targetScene.view({ ...options, level })`,
   which re-enters the wrapper and now passes, because the target scene is `this`. After
   `game.ready` a redirect toasts "Your view follows {actor}" to the player, at most once per 10 s.
   At login it is silent.
4. Not loading, `pass`: set `inflight`, call `wrapped`, clear `inflight`.

This one patch covers:

- the login draw (`client/game.mjs:1069`), so the active scene is never drawn for a pinned player.
  With **no active scene**, core draws `canvas.draw(null)` instead (`game.mjs:1070`), which never
  passes `Scene#view` and fires no `canvasReady` (`board.mjs` `#drawBlank`); pins' `ready` hook
  covers it (`ready: reconcile`, below — `ready` waits for canvas initialization);
- GM activation (`client/documents/scene.mjs:1528`);
- `pullToScene` (`client/documents/collections/scenes.mjs:113`) and "Pull users to scene";
- scene-navigation clicks;
- resume's `scene.view`;
- stock TeleportToken's pull (`teleport-token.mjs:149,152`) and its self-view when the player moved
  the token (`:158`), and portals `teleportParty`'s `pullUsers` (`scene-adapter.mjs:361`). Each of
  these arrives **after** the create, while `createToken: follow`'s draw of the same scene is under
  way, so step 2 drops it silently: no toast, one draw. Their view options (`controlledTokens`, the
  region's `transition`, the level) are lost; `createToken: follow` passes the destination level and
  `controlledTokens: [newToken.id]` when the player owns the token, so only the region's transition
  animation is lost (Known gaps).

**Patch `pins-scene-activate`.** This wraps `Scene.prototype._onActivate`, with marker
`__pentarynPinsActivate`. When `activateDecision` says skip, it returns without calling through.
That covers two cases: activating some other scene, which saves a no-op view and a toast, and
deactivating the scene the pinned player is on, which would otherwise `unview()` to a blank canvas.
Activating a scene calls only that scene's `_onActivate(true)`, so skipping it is sound (verified in
review). `unview` itself is **not** patched, because `Scene#_onDelete` and level deletion must still
blank the canvas.

**Follow hooks.** These run on the pinned player's client. The pinned root actor is looked up again
on every call and never cached, because the token id and the token's `actorId` both change (a hop, a
transform). Each hook first returns when `canvas.scene?.id` and `canvas.level?.id` are already the
target, and otherwise goes through `request`.

| Hook (label) | Does |
|---|---|
| `createToken: follow` | a token whose **root** is the pin was created and is now the character's **only** token: `request({ scene, level }, "move", { controlledTokens: owned ? [id] : [] })`. A second token (a copy, a sidebar drag, the first half of a carry) is not followed (review fix 2026-10-17: a copy is not a move) |
| `deleteToken: follow` | a token of the root was deleted: record a replacement as `latest`, prune `latest`, then recompute the target; when it is on another scene than the viewed one, `request` it (`move` for the replacement or the carried copy, else `reconcile`). If no token of the root remains, **stay** (stock). (Review fix 2026-10-17: the move is followed when it completes, and deleting the copy a player views sends them to the one left.) |
| `updateToken: follow` | the pinned token changed `level` → `request` that level (core's own level follow, `token.mjs:2968`, may start the same draw first; either one then gets `none`). The token's `actorId` changed (a transform or a revert) → reconcile through `request`, which is `none` when the scene is unchanged. The pinned token was moved by **another user** and its centre is now off-screen → `canvas.animatePan` to it. Reads only `changes` and `userId` before the actor check (cheap; not a §5.5 hot hook) |
| `updateUser: pin changed` | own pin flag changed → reconcile. Any user's pin changed → re-render open actor sheets |
| `canvasReady: reconcile` | the switch is on and the token's **scene** is not the canvas's → `settle()` (another level of the token's scene is left alone: `viewDecision` passed it as asked, and a token level change is `updateToken: follow`'s). It **never calls `view` itself**: `canvasReady` runs while `canvas.loading` is still true (`board.mjs:1241` vs `:1251`), so a view from here is always refused. It **never returns false**, because `canvasReady` is `Hooks.call` and resume listens after it. |
| `ready: reconcile` | once, after the API publish: the same as `canvasReady: reconcile`. Covers a login with no active scene (no `canvasReady`) |

During a cross-scene move, both core's (create, then delete with `replacements`) and carryTo's
(keepId create, then plain delete) leave two tokens of the root actor for a moment, possibly with
the same token id. `latest` (by uuid) makes `pickToken` choose the new one, so the redirect never
bounces the player back.

### Coexistence with pentaryn-resume

Change `resume-core.mjs` `resumeTarget(saved, { activeId, sceneExists, pinnedScene = null })`, where
`pinnedScene` is a **scene id string** (the same type as `view.scene`):

- `pinnedScene` null → today's rules, unchanged (all existing rows stay as they are);
- `pinnedScene` set and `view.scene !== pinnedScene` → null (the pin wins);
- `pinnedScene` set and equal → `{ scene, level: null, position }`. The "table moved on" rule does
  not apply, and `level: null` keeps the token's level.

`memory.mjs` `resume()` passes
`pinnedScene: apiOf("pentaryn-pins")?.pinnedToken?.(game.user)?.scene ?? null`, wrapped in a
try/catch that falls back to null. `pinnedToken`'s `scene` is an id string by contract; if it ever
came back as a document, every pinned resume would silently become null, so the contract test pins
the type on both sides (below). **Ordering:** pins registers `Hooks.once("ready")` when its entry
script runs. Resume registers its `ready: resume` listener during `setup`. So pins' API is published
before resume's listener runs. Pin this ordering in a resume glue test, together with the
"pins absent" case. Saving is unchanged: `currentView` records `canvas.scene`, which is the pinned
scene. Declare the read in resume's `describe().flags.reads` (`"api:pentaryn-pins.pinnedToken"`), in
its README "Flags other modules read", and in pins' README.

Resume core rows: pinned and matching with the active scene changed → position, level null; pinned
and not matching → null; `pinnedScene` null → every existing row unchanged. Resume glue: pins absent
→ `golden/hooks.json` and the existing cases unchanged; pinned and matching → no `scene.view`, pans;
pinned and not matching → no pan and **no `resumed` event**.

Docs: `context/foundry/resume.md` lines 24-26 and 38-40, and the resume README "What the player
sees", say: "with pinning on, a pinned player ignores activation and pulls; resume restores only
pan and zoom on the pinned scene".

### GM canvas menu (`canvas-menu.mjs` + `menu-ui.mjs`)

- **Binding** (`canvasReady: bind board`, idempotent through `board.dataset.<px>Bound`):
  - `pointerdown` in the capture phase on `#board`, passive. For `button === 2` it records
    `{ x, y, buttons: ev.buttons, dragging }`, where `dragging` is a snapshot of
    `canvas.currentMouseManager != null` (a left drag or ruler live) **taken now**: core cancels a
    left drag in its own capture-phase `contextmenu` listener (`client/canvas/interaction/mouse-handler.mjs:384`)
    before pins' listener runs, so a check at contextmenu time would always read "no drag". For any
    other button it clears the record (`menuTrigger` → `reset`). No preventDefault, no
    stopPropagation.
  - `pointerup` in the capture phase on `#board`, passive: for `button === 2`, feeds `menuTrigger`.
  - `contextmenu` in the **bubble phase on `#board.parentElement`**, filtered to
    `ev.target === board`: feeds `menuTrigger`. The record is **cleared after every contextmenu**
    that opens or refuses the menu, so a stale record cannot pass the gate later.
  - Why this placement: the portal badge's capture listener calls `stopPropagation` on a badge
    (`pentaryn-portals/badges.mjs:268-269`), so a badge right-click never reaches this listener (or
    any bubble or document listener), whatever the hook order. That is the property pins relies on.
    Core's document-level `contextmenu` `preventDefault` (`client/game.mjs:2141`) does **not** stop
    other listeners; it only suppresses the browser menu. The parent-element listener is chosen for
    scope (board events only, gone with the board), not because a document listener would fail.
- **Trigger** (`menuTrigger`): the menu opens when **both** the contextmenu and the right pointerup
  have arrived after the recorded down. On Windows (BOSS, Joe's main browser) that is at the
  contextmenu, which follows the pointerup. On macOS (the alt host), contextmenu fires at mousedown,
  where the down→contextmenu distance is always 0, so opening there would pop the menu at the start
  of every right-drag pan; waiting for the pointerup makes the 4 px test real on both. A badge
  right-click never delivers the contextmenu, so its pointerup alone opens nothing.
- **Gate** (`menuAllowed`): the user is a GM, the switch is on, `canvas.ready`, the active layer is
  the token layer, the target is the board, a recorded right down with `buttons === 2` and no drag at
  that moment, the release within 4 px of the down (a right-drag pan never opens it), no token under
  the point (all tokens, hidden ones included, for a GM), and no door control under the point. The
  hit test is done in the adapter. The decision is in core.
- **Point**: `pt = canvas.canvasCoordinatesFromClient({ x: ev.clientX, y: ev.clientY })` of the
  release event, captured when the menu opens, together with `canvas.scene.id` and
  `canvas.level?.id`. `canvas.mousePosition` is never read inside an item.
- **Items** (DOM `nav`, `position: fixed` at the click, delegated click, with the badge menu's look
  under pins' own prefix):
  1. **Prompt note**: `apiOf("pentaryn-prompts").place(null, { at: pt })`. Hidden when prompts or
     its `place` is missing.
  2. **Teleport pinned character ▸**: a submenu built from `teleportChoices`. Picking an enabled row
     calls `pins.teleport(user, { x: pt.x, y: pt.y, scene, level })`. Toast
     "{actor} (+N) → {scene}", or warn with the `reason` on failure.
  The menu closes **before** the action awaits, so a double click does nothing. It also closes on a
  pointerdown outside it, on Escape, and on `canvasTearDown`.
- Unchanged: P and Shift+P, right-drag pan, token right-click (HUD), the badge menu, players,
  non-token layers.

## Risks

- **Levels (v14).** carryTo copies `toObject()`, so a cross-scene `teleportParty` (unchanged)
  carries the source scene's level id. `teleportToken` always resolves a level (step 3) and puts it
  in every displace waypoint (step 7). Check live that a token lands on the intended floor.
  **Hit live 2026-10-17 (pins-live S12-S18, "level must exist"):** the risk was real for the
  portal-hop follow too. A follower or party member created with a level the destination lacks
  stands on no floor, and core refuses every later move of it. Resolved in portals 0.6.0: carryTo's
  plain path picks a level the destination has (`carriedLevel`: the PC's floor for the follow, the
  destination region's one floor for Teleport party, else its own id when shared, else the initial
  level). The rest of its data is unchanged.
- **Canvas draw outside `Scene#view`.** A direct `canvas.draw(scene)` bypasses the redirect. So does
  a **bare `canvas.draw()` while `!canvas.ready`**: it draws `game.scenes.current`, which is the
  *active* scene until the canvas is ready (`client/documents/collections/scenes.mjs:40-43`). Core
  does this on scene updates that need a redraw (`client/documents/scene.mjs:1406`) and on level
  deletion (`client/documents/level.mjs:107`). For a pinned player that can draw the active scene
  once; the `canvasReady: reconcile` → `settle()` path then views the token's scene after loading
  clears (one visible bounce, no stranding). Any module or macro that calls `canvas.draw(scene)`
  directly gets the same bounce; say so in the pins README Pitfalls.
- **Hidden scene.** A pinned token on a hidden scene still draws for the player (there is no
  permission check), and the nav bar shows that scene's name to them.
- **Ambiguity.** A pin with two tokens that is not in a transient move gets stock behaviour for that
  player, and the audit warns. Joe reads this in the switch-on toast and in `audit()`.
- **Browser event order.** The pointerdown → pointerup/contextmenu sequence is modelled in the pure
  `menuTrigger` for both orders, but the stub cannot prove real browser order. Check it live in
  Joe's browser on BOSS (Windows) and once on the Mac.
- **Settle timing.** `settle()` polls `canvas.loading`; a scene that takes longer than 120 s to load
  gives up with a warn and the next `canvasReady` reconciles again.
- **Players can clear their own pin** (`flags` on their own User) from the console. This is accepted
  at this table. The audit shows it.

## Known gaps (copy to `context/foundry/pins.md` and the READMEs)

- **Playlist.** A pinned player who ignores an activation still hears the active scene's playlist:
  the playlist change is world-wide, not a scene draw.
- **Combat tracker.** A cross-scene `teleportToken` deletes without `replacements`, so core does not
  remap combatants (`client/documents/combat.mjs:1179`): the PC and its company drop off the tracker
  mid-combat. `teleportParty` already has this. Asked under Open questions; the default is to leave
  it and re-add them by hand.
- **Wild-shaped druid's summons** (existing in portals, inherited, not a regression). `followersOf`
  matches a follower's `summoner` against the leader record's `actorId`, which for a polymorphed
  leader is the form's id, while `summon.origin` names the original druid. So a wild-shaped druid's
  summons do not follow, through portals today or through `teleportToken`. Fixing it in `recordOf`
  is a separate, declared portals change.
  **Fixed 2026-10-17 (portals 0.6.0, finding 4):** `recordOf` carries `rootActorId` while transformed and
  `leaderOf` matches it, so these summons now follow (Regression guard, Portal-hop follow).
- **Region transition animation.** For a pinned player, a portal hop's draw is started by
  `createToken: follow`, so the region's own `transition` from TeleportToken's pull is not used; the
  default scene transition plays instead.
- **macOS Ctrl-click** is a left button with a modifier, not a right press, so it does not open the
  menu; use a two-finger click.
- **`pins.teleport` with the switch off** moves the token but not the player's view
  (`viewFollows: false`, `warning: "VIEW_UNCHANGED"`).
