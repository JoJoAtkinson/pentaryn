# Foundry — domain root

**Read this when:** doing anything in or around Foundry VTT — scenes, actors, tokens, the
server, the tunnel, the updater, the asset pipeline.
**Not this file:** current one-shot state (which scenes exist, who is where, actor IDs) →
[`../space-journey.md`](../space-journey.md) · lore authoring → [`../world/README.md`](../../world/README.md)

> **No dated entries in this file.** Session findings and campaign state go in
> `../space-journey.md`. What lives here is durable: things that stay true after the
> current one-shot ends. This file was 230 lines of both once, and it cost every
> Foundry session a week of stale bed assignments.

## The platform

Foundry **v14.369** (since 2026-10-10) · system **dnd5e 6.0.6** (all four worlds — pentaryn, ardenford, ardenhaven, space-journey; `world.json` systemVersion checked 2026-10-15) · **D&D 2024 rules**

> **This domain is not written for one world.** Everything here applies to **any dnd5e world**
> authored in this setup — the tooling, the modules and the conventions travel; only the content
> changes. Do **not** hardcode a world id in these files or in anything you build from them.
>
> **Ask the live client which world you are in** rather than assuming:
>
> ```js
> game.world.id      // e.g. "space-journey"
> game.world.title   // e.g. "Space Journey"
> ```
>
> The `WORLD=` argument to `make login` is the only place a world name is named on purpose, and
> it is supplied per invocation. Current campaign state — which world is live, who is in it, what
> is built — lives in [`../space-journey.md`](../space-journey.md), never here.

Use the 2024 compendium packs: `dnd5e.spells24`, `dnd5e.equipment24`, `dnd5e.feats24`,
`dnd-players-handbook.*`. Not the 2014 `dnd5e.items` pack unless an item exists only there.

**Tools:** `mcp__foundry__*` for world ops (`eval-js` is the escape hatch).
`mcp__dnd-scripts__*` for SRD lookups, campaign-time math, and repo operations.

## Module APIs (`game.pentaryn`)

Every in-house module publishes one namespace under `game.pentaryn` (senses publishes two). Read
this table before spending an `eval-js` call on `Object.keys(game.pentaryn…)`. Three things a
name will not tell you:

- **The namespace is not always the module's short name** — `rules` is `pentaryn-lookup`, `chain`
  is `pentaryn-senses`.
- **Reads return an object, not an array, and report trouble in it** —
  `await game.pentaryn.rules.search("half cover")` is `{ query, books, total, shown, hits: [...], … }` or `{ error }` — iterate `.hits`.
- **ties reads take a ref, ties writes take documents** — since wave 3 the reads (`read`,
  `inbound`, `known.read`, `attributes.of/ids/known/broken`, `study.beliefs/state/lore`) accept an
  id, name, uuid or token; writes still want the `Actor`. Blueprint modules (a `describe` golden
  below) accept a ref: Actor, Token, uuid, id or exact name; `game.pentaryn.<ns>.describe()` lists
  every method with its params.

The table is generated from each `module.json`, the module's code and its
`test/golden/describe.json`; `make check-context` fails when it is stale — regenerate with
`make foundry-module-index`.

## Stale bridge processes will silently break every MCP tool

Every Claude Code session spawns its own `index.js` MCP server, and the first one also
spawns the singleton `backend.js` that owns the bridge's websocket ports
(31414–31416). **Nothing cleans them up when a session ends.**

On 2026-08-23 a `backend.js` from three days earlier still held all three ports. After
a Foundry restart the browser reconnected to that stale broker, and every bridge tool
timed out — `eval-js`, `get-world-info`, all of them — with no error logged anywhere.
Three current sessions sat there unable to bind.

    make foundry-bridge-status    # who is live, who is an orphan, who holds the ports
    make foundry-bridge-clean     # kill orphans only  (DRY=1 to preview)

**On BOSS the GM tab is a headless bot** (`Claude`, role 3, the `foundry-headless-gm` unit): when
bridge tools fail there, `make foundry-headless-status` is the first check, then
`make foundry-headless-restart` rather than reloading a tab ([`headless-gm.md`](headless-gm.md)).

**`clean` never kills a server whose parent is a live `claude` process.** That
restraint is the point: the obvious fix — kill everything matching `foundry-vtt-mcp` —
severs the tools of every other running session, which is exactly what happened while
diagnosing this. The orphan signal is a dead parent; a live backend under an orphaned
server is the shape that actually held the ports.

`make vtt-up` warns (never kills) when any bridge port is held by an orphan, because a restart
is precisely when the browser reconnects and picks the wrong broker.

**After cleaning, a Foundry tab that is already open must be reloaded** to reconnect,
and the MCP server itself needs a Claude Code restart if it was the one killed.

**Restarting only the broker** (for example to pick up a rebuilt fork `dist/`): `kill -9` the
`backend.js` pid, never a plain `kill`. On SIGTERM the backend exits with code 0, and the
wrapper reads that as "lost the lock" and exits too, which takes the session's MCP tools with
it. After SIGKILL, the next tool call respawns the backend from the current `dist/`. The GM tab
does not reconnect by itself (`autoReconnectEnabled` is off), so either reload it or run
`await foundryMCPBridge.restart()` in its console (done 2026-10-10 for the dnd5e 6 port).
**With more than one live session, the respawn can race:** two wrappers each spawn a backend
within the same second, the loser's backend exits 0 on the lock, and that wrapper exits although it
had already connected to the winner (`wrapper.log`: `backend exited cleanly (likely lock failure),
exiting wrapper`). That session loses its `foundry` tools until a Claude Code restart, and the dead
wrapper's backend can linger as an ORPHAN (`make foundry-bridge-status`; clear with
`make foundry-bridge-clean`). Seen 2026-10-12 (PT PR-2). Restart the broker only when no other
session is mid-call, and expect to restart the session that ran the kill.

## The action log is the promotion mechanism — keep it on

Every write tool call lands in `foundry/logs/mcp-<month>.jsonl` — the fork's tools and,
from the wave-2 fork build, the upstream write tools too — and every `eval-js` call also
lands in the eval log with its stated purpose: `eval.jsonl` up to the wave-2 build,
`eval-<YYYY-MM>.jsonl` after it. That log is how you decide which recurring `eval-js` uses
have earned a typed tool — it is the design's own answer to "what should the tool surface
be". Field lists and phases: [`mcp-fork.md`](mcp-fork.md#environment-and-logs).

**The review is one command:** `make foundry-eval-report` (`SINCE=2026-10-01` narrows it,
`JSON=1` for JSON). It reads both eval names, every `mcp-*.jsonl` and the dnd-scripts
server's `dnd-scripts-<month>.jsonl`, and prints outcomes by phase, the `game.pentaryn.<ns>.<fn>`
paths `eval-js` reaches (the promotion candidates), discovery calls, the top runtime
errors and per-tool counts. Read-only.

All of it is gated on **`PENTARYN_MCP_LOG_DIR`**, set in `.mcp.json` (and, for the
dnd-scripts log, on that server's entry in `.vscode/mcp.json`). If it is unset, the
server logs nothing and says nothing — it was unset from 2026-08-14 to 2026-08-22 and
the gap is simply missing. A restart of the MCP server is needed after changing it.

Sanity check: make one `eval-js` call, then `make foundry-eval-report SINCE=<today>`.

**A `"phase": "transport"` line is a call that never reached Foundry** — module not
connected, dead socket, timeout. Until 2026-08-23 those threw before the log write and
left no line at all, so a session spent fighting a dead bridge read back as a quiet one.
Every other phase comes from Foundry itself, so `transport` is unambiguous. Grepping for
real usage means excluding them: `grep -v '"phase":"transport"' foundry/logs/eval.jsonl`.

**What the log said as of 2026-08-22** (3 days of scene-building, 2026-08-11 → 08-14):
323 `eval-js` calls versus 2 `place-tokens`, and nothing else. 59% of the eval calls
were one-off reads. Treat that as a narrow sample of one kind of work, not a verdict on
the whole tool surface.

**Decision 2026-08-23:** `place-tokens` retired from the fork — the surface is
deliberately **eval-js only**, logging stays on, and the tool question gets revisited
against a clean month of steady-state log (~2026-09-22). Full reasoning and the revisit
criteria: [`../plans/mcp-skill-library.md`](../plans/mcp-skill-library.md).
**2026-10-10:** a second fork tool, `prompt-markers` (one fat tool, `action` enum), fronts the
`pentaryn-prompts` module; only its `replace` action is written to the action log. The same build
added a per-query transport timeout (default still 10 s) and image passthrough for fork tools —
see [`prompt-markers.md`](prompt-markers.md). From module 0.3.0 the module builds `npc`
replacements itself and the tool prints the module's readback text as it is. From 0.4.0 (fork
rebuilt the same day) `replace` also takes `specFile` (a JSON spec on disk) and the dry run previews
characters on an unsaved actor.
**Tools missing from a session** that the backend has (a fork tool added after the session
started): Claude Code caches `tools/list` per session. Wrappers built from 2026-10-10 announce a
changed list (`notifications/tools/list_changed`, polled every 30 s); older sessions need `/mcp` →
reconnect, or a new session. `dnd5e-add-feature` also takes `recharge: 5` (fork).

## Token conventions — applied world-wide

Ring tiers: **gold** `#ffcc4d` PC · **red** `#d8433a` foe · **green** `#86c98a` named/talkable ·
**grey** `#9098a0` mook · **no ring** = crowd.

Subject textures follow Foundry's ⅔ safe-area spec, in
`FoundryVTT/Data/assets/tokens/custom/ring-subjects/`. Muted crowd art lives in
`.../generic-villagers/`. Build one with `scripts/foundry/ring_subject.py`.

**Rotation is locked world-wide.** `lockRotation: true` on every actor prototype and every
placed token, plus `core.prototypeTokenOverrides.*.lockRotation = true` so new tokens
inherit it. Tokens face their art's orientation and never spin toward the direction of
travel. Don't re-enable per-token without asking.

**A ringed token draws `ring.subject.texture`, not `texture.src`.** Re-art one without the
subject and it silently keeps the old picture — looks like a stale client, isn't. Placed
tokens don't inherit prototype changes either. See `scripts/foundry/README.md`.

**A ringless crowd token draws the opposite field — `texture.src`.** So crowd art gets the
⅔ subject webp in **both** `texture.src` and `ring.subject.texture`; point `texture.src` at
the raw art and the crowd renders 1.5× the ringed NPCs beside it. Sweep snippet in
`scripts/foundry/README.md`.

**Standing quirk:** derived token/actor data goes stale after writes. Verify with
`actor.reset()` or `await canvas.draw()`, never by reading `_source`.

**A token move "not persisting" is our hidden tab, not a Foundry bug.** The MCP tab is hidden,
so token animation never advances and the placeable's `tok.x`/`tok.y` keep the old position
while the document and the server hold the new one. Position is source data, not derived: read
`tokenDoc._source.x/y` or the server, or update with `{animate: false}`. No throwaway first move
is needed (wave 3, 2026-10-13, clean-world check).

**Possession is marked per-token, not per-actor** (`pentaryn-ties`). Token HUD →
masks-theater button, GM-only, `token.flags["pentaryn-ties"].worn = {by, note}`. Never mark
a host on the actor — the same actor appears in more than one scene, and the ties graph must
keep showing the *host's* own relationships. See [`../plans/foundry-npc-ties.md`](../plans/foundry-npc-ties.md) for the design, and the module's own README to use it.
